# Classic Drop 后续功能规划

Status: planned

## 目标

基于当前仓库内容，为 Classic Drop 整理一份分阶段的功能与质量路线图。原始版本用于规划；用户随后已确认进入开发流程。本文件记录产品边界与验收目标，实际进度以 [开发清单](development.md) 和 Git 提交为准。

## 范围假设

- 近期产品按根目录 `README.md` 和 ADR-0175 理解：macOS 上为 Apple 原厂固件 iPod Classic 追加音乐。
- 用户已明确要求增加音乐批量删除：按标题、艺人、专辑、风格、年份和播放列表检索，多选后加入同一个待删除清单，最后统一复核并一次执行。
- 删除采用可恢复模式；删除后不立即释放 iPod 容量。应用应能恢复最近一次删除。
- 用户已明确要求增加导入时的重复音乐检查；检查本批待导入文件之间，以及待导入音乐与当前 iPod 曲库之间的重复。
- 用户新增要求：UI 与最新版本 macOS 的视觉效果一致；本轮仅设计，详见 [macOS 界面设计提案](ui-design.md) 与 [静态视觉稿](ui-concept.svg)。原生保真度、旧系统回退和实际接入方式需在实施前验证。
- 用户新增要求：增加中文、日语和英语界面支持；详见本稿 P1 多语言章节。多语言实现已在本机工作区完成一版，但尚未包含在本次公开文档提交中。
- 保留只读发现与曲库浏览、用户确认后追加、导入时保留既有曲库、可恢复导入等安全约束；删除只作用于用户明确审阅的 Track 集合。
- `src/iOpenPod`、`src/iPodDB`、`src/storage` 是复用的上游实现；上游 iOpenPod 的广泛路线图不自动成为 Classic Drop 的产品承诺。
- 用户尚未确认是否希望把路线图扩展到整个 iOpenPod，因此本稿优先规划 Classic Drop。批量删除首期只针对普通音乐 Track；Podcast、Video 和 Audiobook 暂不纳入。

## 当前已有能力

- 发现并选择 iPod Classic；选择和预览阶段保持设备只读。
- 读取现有曲库，按列表或专辑浏览，并搜索标题、艺人、专辑。
- 从文件或目录导入音频；支持兼容格式复制和不兼容格式转码。
- 预览重复项、编辑有限的曲目元数据、替换或移除待导入项目的封面。
- `src/classic_drop/engine.py:147` 的预览已检查本批原始文件 SHA-256、设备关联的历史导入收据，以及标题/艺人/专辑一致且时长差小于 1,500 ms 的疑似匹配；`tests/classic_drop/test_engine.py:81`、`:90` 和 `tests/classic_drop/test_window.py:28` 有对应的基础回归测试。历史收据只结合当前曲库中的目标路径与大小核对，不能替代设备现存文件的完整内容验证。
- 经用户确认后追加到现有曲库；提供上次导入恢复和安全弹出。
- 现有曲目列表搜索覆盖标题、艺人、专辑、专辑艺人，专辑卡片搜索另包含年份；尚无结构化的六维筛选或待删除清单。
- 虚拟设备测试覆盖追加保留、签名封面、重复项、源文件变化、取消和恢复；UI 测试覆盖浏览、忙碌状态和断开设备清理。

主要依据：`README.md`、`CLASSIC_DROP.md`、`docs/adr/0175-classic-drop-append-only-macos.md`、`src/classic_drop/engine.py`、`src/classic_drop/window.py` 和 `tests/classic_drop/`。

## 需要先澄清的项目边界

根目录 README 将产品定位为 Classic Drop；`AGENTS.md`、`CONTEXT.md`、`GLOSSARY.md`、`docs/source_architecture.md` 和 `TODO.md` 仍以 iOpenPod 2.0 为主。`pyproject.toml` 的发行项目名也是 iOpenPod，而当前 GitHub release workflow 构建并发布 iOpenPod 包。建议先确认此仓库接下来是以 Classic Drop 为主产品、维护两个产品，还是回到 iOpenPod 主线，再决定哪些文档和发布入口需要整理。

批量删除已纳入本路线图，但和 ADR-0175 的 append-only 决策冲突。开始编码前应新增并接受一个 ADR，明确 Classic Drop 的删除范围、恢复语义和 Storage Transaction 顺序；该变更不能只靠修改 UI 绕过 ADR-0175。

README 将在线封面查询列为可选路线，同时范围章节排除在线元数据查询。应先明确在线封面是否属于允许的窄范围，以及隐私、网络失败和来源展示要求；它不属于当前已确认的删除需求。

## 建议优先级

### P0：确认产品边界与发布身份

决策并记录产品范围、目标用户、平台、设备族，以及 Classic Drop 与 iOpenPod 的关系；据此整理入口文档和 release 目标。不要把 Shuffle、iPod touch/iPhone、云服务等 TODO 自动纳入 Classic Drop。

验收条件：

- 根目录 README、项目 Agent 指南、CONTEXT 和产品 ADR 对当前主产品、支持平台与不支持范围没有互相矛盾的描述。
- 明确 `classic-drop` 与 `iopenpod` 是否共享发行版本、CI 发布流程和安装包。
- 删除功能已确认纳入；开始实现前完成独立设计与 ADR 更新。联网封面查询仍需单独决定是否纳入。

### P1：多维筛选与可恢复批量删除

在独立的删除工作区中加入文本检索和结构化筛选：标题、艺人、专辑、风格、年份、播放列表。跨维度条件按 AND 组合；同一维度内多选值按 OR 组合。年份缺失、风格缺失应可显式筛选，不把年份 0 展示为真实年份。列表支持多选，并允许把当前选择或全部筛选结果加入一个累积的“待删除清单（删除包）”。切换筛选条件不会清空清单；重复加入同一 Track 只保留一项。用户可以从清单移除单项或多项、清空整个清单，再继续添加；这些操作只修改内存中的意图。加入的是当时匹配的明确 Track 集合，后续不根据筛选条件自动扩大删除范围。首期只维护一个当前删除包，不包含可复用的命名包或跨会话保存筛选规则。

清单绑定当前 Active iPod 和 Library Snapshot/source revision，断开、切换设备或曲库版本变化时必须清除或要求重新确认，不能把旧 Track ID 用到新曲库。

从播放列表筛选并加入的 Track 表示从整个 iPod 曲库删除：其所有 Playlist occurrences 都会移除，而不是只取消当前 Playlist 的成员关系。先基于确定清单准备一个 Library Review，再展示逐曲标题、艺人、专辑、来源筛选条件、总曲数、预计恢复数据大小及受影响的 Playlist 数量；用户最后确认后仅提交该已审阅的 Review，执行一个 Storage Transaction。清单若改变则使原 Review 失效，必须重新准备。界面应明确标注这是可恢复删除、被移除音乐仍占设备空间，并提供恢复最近一次删除的操作。首期不提供永久清理恢复数据的按钮。

“一次全部删除”指一次提交本次删除包内所有音乐，绝不默认选中整个曲库。执行过程分为验证、准备、发布、校验与完成；进入发布阶段后不能把普通取消当成已回滚，需根据事务结果给出完成或待恢复状态。

当前底层已有可复用能力：`LibraryWorkspace.remove_tracks()` 按 Track ID 批量移除并清除所有 Playlist occurrences；`LibraryPreparationRequest` 支持 `delete_omissions`；Library/Storage 测试覆盖恢复式移除、共享媒体保留及失败路径。Classic Drop 仍需新增筛选、选择、待删除清单、复核、执行状态和恢复入口。

恢复策略存在明确差异：`src/classic_drop/engine.py:78` 配置 Host Recovery，而 ADR-0167 允许先把原件保留到电脑，再回收设备上的空间。它不能直接满足本次“恢复数据留在 iPod、不立即释放空间”的选择。新 ADR 应为删除流程选择 Storage 已保留的设备端恢复策略，确认 Library 协调层能以隔离且明确的策略接入，并保证已提交的删除恢复数据不会在普通重连或自动清理中被回收；若需要调整公共接口，先单独提出并确认，不能悄悄更改全局导入策略。设备端保留原件仍可能需要额外的数据库、日志与回滚空间，容量不足时应在发布前拒绝。

导入恢复与删除恢复必须共享明确的操作顺序约束。建议首期只允许存在一个可撤销的末次曲库写操作：成功删除后，继续导入或再次删除前先要求恢复本次删除；不自动覆盖旧恢复记录，也不在没有告知的情况下让“撤销上次导入”跨过一次删除。恢复后重新读取曲库，清空旧删除清单与 Review。若外部程序已修改相关内容，拒绝覆盖并保留恢复证据。该限制是待开发前批准的设计建议，不是已经实现的行为。

建议落点：新增 Classic Drop 删除筛选/清单状态模块，扩展 `src/classic_drop/window.py` 的独立工作区和 `src/classic_drop/engine.py` 的 review/save/recovery 协调；使用 Track ID、Library Snapshot 和现有 Workspace revision，不直接拼接设备路径或调用文件删除接口。

验收条件：

- 可按标题、艺人、专辑、风格、年份和播放列表筛选普通音乐；跨维度 AND 与同维度多选 OR 的组合规则有测试。
- 可多选并分批加入同一个待删除清单，筛选切换不丢选择，重复加入不重复计数；全部筛选结果加入前显示匹配数量。
- 删除包可单项/多项移出、清空；清空后不能提交。新增筛选匹配项不会自动加入已经组好的包。
- 清单冻结到来源设备和 Library Snapshot；来源变化时拒绝提交并要求重新读取/复核。
- 最后确认只发起一次已审阅 Library 保存；删除只经现有 Storage Transaction 完成，既有未选 Track、其元数据和共享媒体保持不变。
- 被删除 Track 在所有 Playlists 中的 occurrence 都被移除；Playlist 本身、未选歌曲及对应 Artwork 仍正确保留。
- 删除成功后可恢复该批曲库和媒体；恢复失败/设备断开显示可恢复状态与下一步。界面明确说明恢复数据占用空间。
- 重启应用、重连和安全弹出后恢复记录仍可发现，设备端音乐原件不被普通终态清理自动删除；后续导入/删除不能使末次删除恢复记录悄悄失效。
- 多个 Track 共享同一媒体文件时，不移走仍被未选 Track 引用的文件；恢复数据大小按实际保留的唯一文件计算。
- 预览和组包不写设备；事务中断后的行为遵循 Storage journal/recovery，不宣称多文件发布具备瞬时全局原子性。

### P1：导入时的重复音乐检查

在已有查重基础上补齐明确的匹配结果和处理流程。覆盖一个导入会话内分批添加的所有文件，并与当前 Active iPod 的曲库比较；不能只比较最近一次添加的批次。结果区分“新增”“确认重复”“历史导入记录匹配”“疑似重复”“检查失败/未完成”，展示匹配对象、来源（本次队列或 iPod 曲库）、标题、艺人、专辑、时长及判断依据。只按文件名或相同标题不应认定确认重复。

建议的匹配层次：

1. 本批精确检查：使用原始文件 SHA-256 识别相同内容的不同路径或文件名；同一文件反复添加不增加队列项。每组默认只保留一个待导入项，允许改选组内代表文件。
2. 已有曲库快速检查：使用当前 Library Snapshot 的曲目信息和已有 ImportHistory 收据寻找候选；标题、艺人和时长用于候选匹配，专辑及版本描述作为区别证据。已有的 1,500 ms 阈值属于现行行为，是否保留需通过短曲、现场版、重录版样本确认，不能把它当作音频相等的证明。缺少标题、艺人或有效时长时不能据空值一致强判重复。
3. 已有曲库确认：仅在需要时通过 Storage 对候选设备文件做只读内容验证；原始文件 SHA-256 与目标文件一致可标记确认重复。转码、重新打标签或不同格式会改变整文件哈希；这种情况下只能保留历史来源证据或疑似匹配，不宣称已证明音频相同。首期不引入音频指纹或在线识别。

默认对确认重复和历史/疑似匹配取消勾选，同时提供“跳过”与显式“仍然导入”；用户选择代表文件或决定继续后，应保留其选择，不能被后续添加文件静默重置。支持筛选重复状态、查看匹配组并批量跳过重复项。最终导入确认显示新增、重复跳过、疑似待处理及实际勾选的数量；如果仍有疑似或已知重复被选中，明确提示用户正在继续导入这些项目。

查重和批量删除是独立的选择集合：导入查重不删除或替换 iPod 既有音乐，也不自动把匹配项加入删除包。删除成功后使用重新读取的当前 Library；仅存在于恢复数据中的音乐不能被当成仍在曲库中的 Track 而拦截重新导入。若前述恢复顺序限制尚未解除，仍应先遵循该写入限制，不能通过查重绕开。

建议落点：提取 Classic Drop 查重规则与结果模型供 `engine.py` 的预览/提交使用，复用 `history.py` 作为提示来源；在 `window.py` 展示匹配详情、状态过滤和批量处理。以当前曲库字段构建候选索引，避免对每个源文件逐一遍历整个曲库；不要求每次导入都对 iPod 所有媒体进行完整哈希。查重在后台执行并可取消，匹配缓存绑定设备身份、曲库版本和文件内容观察，缓存不授予写入权限。是否把精确查重前移到转码前，按现有媒体捕获接口可复用程度决定，避免重复读取或转换同一文件。

验收条件：

- 同一文件重复添加、同字节不同文件名、重叠目录及多轮追加的队列都能正确查重，数量不会因重复路径增加。
- 能显示与本次队列及 iPod 曲库的匹配对象和依据；同名不同艺人、现场/录音室版本、不同专辑或格式、缺失标签不被错误标为确认重复。
- 旧收据对应歌曲已从曲库删除，或路径/大小/已验证内容发生变化时，不继续显示为可靠的现存重复。
- 确认重复默认跳过；历史或疑似重复默认未勾选，用户可以显式继续导入；更换筛选或追加文件不丢失用户决定。
- 用户修改预览标签后，元数据匹配建议更新，但既有原始内容匹配事实不会因为改标题消失；重新检测不会静默替用户改变已确认选择。
- 检查失败与取消必须清楚显示，不能把未完成检查显示为“无重复”；检查阶段保持 iPod 只读。
- 源文件或曲库变化使相关结果失效，提交前依现有源验证重新校验；虚拟设备测试验证跳过行为和未选/既有曲目保持不变。
- 删除与恢复后重新读取曲库再查重；导入重复判定不能触发删除，也不能把恢复数据中的原件错误当作当前曲库成员。

### P1：简体中文、日语、英语界面

Classic Drop 当前界面主要使用简体中文文案，启动入口直接建立 QApplication，尚未挂接应用翻译管理器，也没有 Classic Drop 自有语言目录。上游 iOpenPod 已提供以英文为源语言的 Qt QTranslator 管理、运行时切换和 .ts / .qm 工具链，并维护德语和西班牙语目录；可借鉴其维护流程，但不能把 Classic Drop UI 当成已经自动继承或覆盖上游 GUI 语言。当前上游界面实现未被 Classic Drop 启动入口调用。

建议首期完整支持 English（源语言）、简体中文（zh_CN）、日本語（ja_JP）三种应用界面语言，不承诺繁体中文或更多区域变体。首次启动跟随 macOS 首选语言：匹配简中或日语时使用对应译文，其他情况退回英文；偏好设置提供“跟随系统 / 简体中文 / 日本語 / English”持久选择，手动设置优先于系统。语言设置属于应用，不写入 iPod。

本地化覆盖应用菜单、工具栏、工作区、按钮、筛选项、空状态、确认 Sheet、恢复/断连提示、错误/进度/状态消息、帮助文案、可访问名称、列名、日期/数字/容量格式和系统对话框可译文案。英语保持源文案，简中与日语提供审核后的 Qt .ts 源文件和随应用发布的 .qm 文件。首期不在线机器翻译，也不在运行时请求网络。

翻译只改变 Classic Drop 的 UI 呈现，不翻译曲目名、艺人、专辑、风格、播放列表用户数据、文件名/路径、设备标识、固件文本和原始诊断信息。Track、Library、Playlist、待删除清单/删除包等关键术语在三种语言中共用术语表，特别区分“把歌曲从整个曲库删除”和“只移出播放列表”。

切换语言应立即重新绘制可见控件和动态消息，但保留导入队列、重复匹配与人工决定、编辑未提交值、筛选条件、删除包、进度/取消状态、设备选择和恢复选择；不可因重新翻译清空或重建业务状态。无翻译项安全回退英文；正式 catalog 不得带未审核的 unfinished 键。窗口宽度、表列、Sheet 和错误文字适配日语/英语文案长度与字体回退，避免截断关键危险提示。

建议借鉴 Qt Linguist、QTranslator 和仓库现有提取/编译维护思路，但为 Classic Drop 使用独立 catalog 命名空间和启动配置，避免误装上游 iOpenPod 的 es/de catalog 或共享其语言设置。英语作为 source 时需一次性整理当前中文硬编码文案，再维护简中/日语 catalog；PyInstaller 需明确纳入两份编译目录。具体代码复用边界和工具可用性在实现规划阶段验证，不在本轮更改依赖。

验收条件：

- 首次启动及区域变体检测按约定选出简中、日文或英文；不支持区域与偏好无效时稳定回退英文。
- 语言选项及当前选中项有完整可翻译名称，手动设置重启后仍生效并覆盖系统自动选择。
- 主窗口、导入、查重、设备状态、删除、确认 Sheet、恢复和故障提示不存在用户可见的遗漏文案；正式 catalog 无未审核的 unfinished 项。
- 切换语言立即更新静态、动态、模型和辅助功能文字，保留队列/编辑/筛选/删除包/恢复状态等内存状态。
- 有占位符、复数、标记文本、日期/数值及菜单快捷键一致性检查；日文和英文长文案不会遮挡确认按钮、危险提示或数量。
- packaged macOS app 离线启动时可找到三语；原始用户曲目元数据、设备标识、路径与诊断细节原样保留。
- 在 macOS 上验证系统首选语言、手动覆盖、浅/深色和最小窗口；目录发现与编译运行用自动化验证。

### P2：低剩余空间的导入预估

在导入预览中显示设备可用空间、所选内容规模和保守的预计写入量。复制文件可依据源内容大小；转码、封面、数据库更新及事务临时空间要纳入估算或明确标成估算范围。现有设备信息已显示可用空间，但预览没有把它与本批写入需求关联起来。

建议落点：`src/classic_drop/engine.py` 的 `preview` / `commit`、`src/classic_drop/window.py` 的队列状态与导入确认；估算规则应尽量复用 Storage / iPodDB 已有的准备结果，不重复实现格式知识。

验收条件：

- 预览能同时显示可用空间和本批预计新增空间；转码与附加数据的估算假设可解释。
- 当预计需求超过可用空间时，导入不能静默开始，并提供明确原因。
- 预览本身仍不修改 iPod；虚拟设备测试验证足够空间、空间不足、转码和封面场景。

### P2：真实设备覆盖与 Classic Drop 可发布性

当前文档以 A1238 SSD 设备为已知验证场景，并明确其他机型、Intel Mac 和安装包签名仍待验证。现有 release workflow 的产物和校验对象是 iOpenPod；`packaging/classic-drop.spec` 有独立 bundle 定义，但尚未接入该发布流程。

验收条件：

- 建立设备验证表，记录机型标识、固件、存储类型、macOS 版本和 CPU 架构；未知组合清楚标为未验证。
- 对 Classic Drop `.app` 增加独立构建、包外启动 smoke test 和必要的签名、公证检查。
- 每个新增支持组合至少验证发现、读取、少量追加、iPod 端播放/封面读取和恢复；硬件测试在完整备份后执行。

### P2：故障路径与恢复体验

补足导入和批量删除应用层对设备中途断开、准备失败、事务未确认完成、恢复记录不可用、主机收据写入失败等情形的用户反馈与测试。现有 Classic Drop 测试已有源文件变化、提交前取消和成功导入恢复覆盖；上游测试已覆盖部分 Track 删除事务，但尚未覆盖 Classic Drop 的跨筛选组包和删除恢复 UI。

验收条件：

- 对关键写入阶段的取消、断开和恢复结果有虚拟设备回归测试。
- 失败后能区分“设备状态未知 / 可重试 / 需要恢复 / 本地记录失败”，提供下一步操作和恢复记录位置。
- 所有设备写入仍只通过 Storage；不新增绕过事务的直接文件写入。

### P2：拆分过大的界面与协调模块

`src/classic_drop/window.py` 约 1,000 行，包含窗口构建、导入队列、曲库列表/专辑视图、状态处理和关闭流程；`engine.py` 约 350 行，包含发现、选择、预览、追加和恢复。项目工程规则对文件长度设有 300 行上限。建议在后续功能扩展前按职责拆分，并保持行为不变。

验收条件：

- 界面构建、曲库浏览、导入队列和状态/worker 协调有清晰边界。
- 导入准备、事务提交与恢复的职责可独立阅读和测试。
- 现有 `tests/classic_drop/` 全部保持通过；重构不改变公开行为或 ADR-0175 的安全约束。

### P3：经决策后再扩展产品行为

- 若用户确认需要在线封面：只请求必要信息，展示来源和匹配置信度，允许完全离线使用，并测试超时、无匹配和错误响应。
- 大型曲库性能先建立有代表性的加载耗时基准；若 `QTableWidget` 全量填充和过滤成为可复现瓶颈，再考虑切换模型/视图，不预先做无数据支撑的优化。

## 主要风险

- 数据库和封面行为依赖机型与固件；虚拟文件系统通过不等于 iPod 实机兼容。
- 空间预估无法完全预测文件系统、数据库和事务临时空间，必须保留安全余量并明确估算性质。
- 相同标签和相近时长可能属于不同录音，相同音频也可能因格式/标签不同而具有不同文件哈希。确认重复与疑似匹配必须分开，首期不承诺识别所有音频等价情况。
- 可恢复删除会把音乐文件保留在设备恢复数据中，因此不会立即释放设备空间；未来若增加永久清理，必须作为另一个不可逆操作单独授权。
- 按 Playlist 筛选可能让用户误以为只会移出 Playlist；最终复核必须明确该 Track 会从整个 Library 和所有 Playlists 移除。
- 删除过程中各数据库/文件变更按事务顺序发布，断电时不保证所有文件在同一瞬间切换；需要清楚呈现事务恢复状态。
- 删除和支持更多设备会扩大现有“macOS + Classic + append-only”边界，需先更新产品决策。
- 同仓库存在上游 iOpenPod 的独立发行链，错误复用其版本或发布 workflow 可能产生错误产品包。

## 建议执行顺序

1. 先由维护者确认 P0 的产品与发行边界；批量删除已获需求确认，在线封面仍待确认。
2. 为可恢复批量删除新增 ADR，锁定筛选组合规则、Playlist 全局删除语义、恢复行为及不立即释放容量的提示。
3. 先验证设备端保留恢复数据、重连与终态清理策略能够满足需求，再实现独立的多维搜索和待删除清单；复用 LibraryWorkspace、Library Review 与 Storage Transaction，删除恢复链作为同一阶段的验收内容。
4. 补足多选/分批加入、过期清单、批量删除事务失败、断开和恢复的虚拟设备回归测试，再进行实机小批量验证。
5. 完善导入查重的分层结果、匹配详情、跨批次队列处理与提交前复核，并覆盖误判、源变化及删除/恢复后的联合回归；该项可独立于删除流程的开发推进，但整合后必须验证两者互不影响。
6. 多语言基础与 UI 迁移同步推进：建立 Classic Drop 独立英语源文案、简中和日语 catalogs 与打包验证，让新增查重/删除界面直接进入三语覆盖。
7. 之后推进低空间导入预估、Classic Drop 专属 macOS 发布验证和模块拆分。
